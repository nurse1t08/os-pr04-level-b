# Практическая работа № 4 — уровень B

**Тема:** сравнение `threading` и `multiprocessing` для CPU-bound и I/O-bound работы.

## Запуск

```bash
bash run.sh
```

Скрипт генерирует `numbers.txt` с **10 миллионами** целых чисел, затем выполняет каждый тест 3 раза. Для короткой проверки: `python3 gen_numbers.py --count 100000 && python3 benchmark.py --repeats 1`. Результаты сохраняются в `results.csv`. В репозиторий включён пример **реального запуска в тестовой Linux-среде на 10 млн чисел**; на вашем компьютере времена будут другими. Требуется Python 3.11+; внешних библиотек нет. Лучше запускать в Ubuntu и без других тяжёлых программ. Использование диска при чтении/генерации не входит в замеры.

## Что сравниваем

| Нагрузка | Последовательно | 4 потока | 4 процесса |
|---|---|---|---|
| Сумма чисел | Python-цикл | `ThreadPoolExecutor` | `ProcessPoolExecutor` (fork) |
| 20 URL | `urllib.request` | `ThreadPoolExecutor` | `ProcessPoolExecutor` (spawn) |

В сетевом тесте поднимается локальный HTTP-сервер с предсказуемой задержкой; доступ в интернет не нужен. Измеряем медиану трёх запусков, выводим число CPU (`os.cpu_count()`). Результат зависит от ОС, нагрузки машины и версии CPython.

## Результаты проверочного запуска (10 000 000 чисел, 3 повтора)

| Способ | Медиана |
|---|---:|
| CPU, 1 поток | 0.3282 с |
| CPU, 4 потока | 0.3248 с |
| CPU, 4 процесса | 0.1932 с |
| I/O, последовательно | 1.6290 с |
| I/O, 4 потока | 0.4123 с |
| I/O, 4 процесса | 1.5499 с |

Контрольная сумма CPU: `4 995 000 000`; 20 ответов в I/O во всех вариантах совпали. Запуск произведён в тестовой Linux-среде на 5 доступных CPU, а не на вашем устройстве. Точные числа и число повторов хранятся в `results.csv`.

## Объяснение

В обычной сборке CPython с GIL CPU-bound Python-цикл не ускоряется от нескольких потоков: байткод Python в каждый момент выполняет лишь один поток. У процессов отдельные интерпретаторы, поэтому на многоядерном CPU вычисления действительно могут идти параллельно, но создание процессов и IPC имеют накладные расходы. При скачивании файлов потоки помогают, потому что ожидание сети освобождает GIL. Для коротких задач создание процессов может оказаться дороже работы.

## Разделение памяти

В программе видно: после изменения списка из потока родитель получает `[2]`, после изменения того же списка процессом родитель **по-прежнему** видит `[2]`. Потоки делят адресное пространство, процессы — нет (при fork вначале работает COW).

## Вывод

Потоки удобны для ожидания ввода-вывода, процессы — для параллельного CPU-bound Python-кода. Конкретные времена берутся из `results.csv` после запуска.
